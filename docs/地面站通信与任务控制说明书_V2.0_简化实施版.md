# 地面站—ESP32-S3—Jetson Nano—MSPM0 通信与任务控制说明书

版本：V2.1（审查修订版）
适用工程：TJC X2 串口屏、ESP32-S3 地面站、Jetson Nano、MSPM0G3507 小车控制器

---

## 1. 文档目的

本文用于指导 Codex 完成地面站到小车的完整控制链路开发。

地面站的核心职责是：

1. 发布手动运动命令。
2. 发布定距、定角度、循迹等离散动作。
3. 发布预设任务。
4. 显示车辆状态、任务进度和故障。
5. 提供取消、停止和急停能力。

本文不要求第一版实现工业级多客户端控制、复杂认证、控制租约、请求缓存恢复或远程互联网访问。

第一版目标是先完成一条清晰、可靠、容易调试的控制链路：

```text
TJC X2 串口屏
    ↕ UART
ESP32-S3 地面站（Wi-Fi AP）
    ↕ Wi-Fi / TCP / JSON
Jetson Nano 任务控制器
    ↕ UART / 二进制协议
MSPM0G3507 实时运动控制器
    ↕
电机、编码器、循迹传感器、IMU
```

ESP32-S3 和 TJC 位于地面站一侧；本说明书中的 SoftAP 是**地面站
ESP32 建立的热点**，Nano 位于车上并作为 Station 接入。不能将 ESP32
同时描述成“地面站”和“车载热点”，否则现场布置、供电和断链责任会混乱。

## 1.1 审查结论、传输选择与当前协议边界

### TCP / UDP 结论

在室内约 10 m、只有一个地面站、命令频率不高于 10 Hz、需要明确
`accepted / done / failed` 结果的场景，第一版使用 **Wi-Fi + TCP 长连接**。
TCP 的有序、可靠传输和现有的长度前缀足以满足控制命令与状态回传；UDP
不会让定距、转角或任务启动更可靠，反而需要额外实现序号、去重、重传、乱序
处理和超时规则。

TCP 不是安全急停通道：Wi-Fi 干扰、发送缓存或 TCP 断连都可能使无线命令
延迟或丢失。因此无线 `estop` 只能作为补充，车辆必须保留独立的物理急停和
MSPM0 本地失联停车。两端应使用非阻塞发送队列和 `TCP_NODELAY`；手动刷新
和普通状态不得在应用层排队堆积。以后若增加视频，可单独使用 RTP/UDP；不要
为控制命令另开 UDP 通道。

### 本文与当前 Nano—MSPM0 V1.1 的对齐规则

本说明书定义的是 ESP32—Nano 上层协议，不能假定 Nano—MSPM0 已经具有相同
能力。以仓库中的《Nano-MSPM0运动控制接口设计书》V1.1 和当前固件能力为准：

| 上层能力 | 当前 V1.1 状态 | V2.1 实施要求 |
| --- | --- | --- |
| `arm`、`clear_fault`、`estop`、`cancel` | 已有 | Nano 按 V1.1 的异步事务和终态转发 |
| `drive_distance` | 已有，但只接受正距离 | “后退”在增加并验证 V1.2 有符号距离前必须在 UI 禁用 |
| `turn_relative` | 已有，正数为右转、负数为左转 | 上层和界面必须采用这一方向，不能另行反转 |
| `follow_line` | 已有 `manual/line_end/cross/corner/distance` | `lap_count` 不是通用完成条件；超时是失败保护，不是成功条件 |
| `manual_drive` | **未实现** | 必须先在 Nano—MSPM0 协议和 MSPM0 固件中增加受限的底盘速度命令；禁止用重复的定距命令模拟手动控制 |
| `stop`、`disarm` | 没有独立串口命令 | `stop` 由 Nano 映射为针对活动事务的 `CANCEL`；`disarm` 只能是 Nano 的上层准入锁，不能冒充 MSPM0 已失能 |
| `run_task` | Nano 本地任务可以实现 | 任务仅可调用已协商的运动原语；不能假定 MSPM0 已支持 `RUN_PROFILE` |

本节优先级高于后文示例。若要增加手动速度、倒车、圈数或 MSPM0 内置 Profile，
必须先更新 Nano—MSPM0 协议说明、Nano 串口客户端、MSPM0 固件和相应测试，
再开放地面站按钮。

## 2. 总体设计原则

### 2.1 控制分层

各模块必须严格分工。

| 模块 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| TJC 串口屏 | 按钮、参数输入、任务选择、状态显示 | 运动控制算法、协议仲裁、电机 PWM |
| ESP32-S3 | 串口屏适配、Wi-Fi 热点、TCP 服务、JSON 转发、连接状态显示 | 电机控制、任务流程、循迹算法 |
| Jetson Nano | 命令校验、任务调度、预设任务执行、状态汇总、与 MSPM0 通信 | 电机 PWM、编码器实时闭环 |
| MSPM0G3507 | 电机控制、速度闭环、循迹、定距、转角、故障停车 | Wi-Fi、TCP、JSON、界面逻辑 |

### 2.2 地面站发布“动作意图”

地面站不得直接下发左右轮 PWM。

正确形式：

```text
前进
后退
左转
右转
停止
前进 500 mm
左转 90°
开始循迹
执行任务 1
取消任务
急停
```

错误形式：

```text
左轮 PWM = 231
右轮 PWM = 214
```

电机 PWM、左右轮速度补偿、PID、编码器闭环均由 MSPM0 负责。

### 2.3 第一版优先简单可靠

第一版保留：

- TCP 长连接。
- 消息长度前缀。
- 地面站会话编号和命令编号。
- 心跳。
- 自动重连。
- 急停高优先级。
- 手动控制超时自动停车。
- accepted / done / failed 状态反馈。
- 单客户端。
- 单一活动运动任务。

第一版不实现：

- HMAC 双向认证。
- controlToken。
- 控制租约 leaseId。
- 多客户端抢占。
- 64 条请求去重缓存。
- 断电后恢复未完成动作。
- 互联网远程控制。
- 复杂权限系统。
- 任务脚本由串口屏动态编辑。

## 3. 控制模式

系统支持三类控制。

### 3.1 手动连续控制

用于地面站方向按钮：

- 前进
- 后退
- 左转
- 右转
- 左前
- 右前
- 左后
- 右后
- 停止

这项能力的前提是 Nano—MSPM0 已完成并验证受限的 `MANUAL_DRIVE` 命令。
在当前 V1.1 基线阶段，手动方向控件必须显示为不可用；不得通过连续发送
`drive_distance` 伪造“按住运行”。

手动控制不是只发送一次后永久执行。

ESP32 必须在按钮保持按下期间，周期发送 `manual_drive` 命令。

推荐刷新周期：

```text
100 ms
```

Nano 如果超过以下时间未收到新的手动控制刷新：

```text
300 ms
```

必须向 MSPM0 下发停止命令。

这样即使：

- 用户松开按钮但 release 事件丢失；
- ESP32 重启；
- Wi-Fi 断开；
- TCP 断开；

车辆也会自动停止。

### 3.2 离散运动

离散运动只发送一次，由 MSPM0 自主执行至结束。

支持：

- 定距直行（当前 V1.1）。
- 定距后退（仅在有符号距离扩展验证后）。
- 相对转角。
- 循迹。
- 停止当前动作。
- 取消当前任务。

示例：

```text
前进 500 mm，速度 200 mm/s
左转 90°，最大轮速 150 mm/s
以 300 mm/s 循迹至指定十字或直角
```

### 3.3 预设任务

预设任务逻辑存放在 Jetson Nano，不放在 TJC，也不放在 ESP32。`run_task`
只是在 Nano 已部署的任务集中选择一个任务；它不是通过 Wi-Fi 发布或热更新
Python 代码的机制。比赛前应将任务文件/程序部署到 Nano，并在 `hello_ack` 或
状态中显示任务配置版本（或哈希），以免界面任务号与车上代码不一致。

地面站只需要发送：

```json
{
  "cmd": "run_task",
  "taskId": 1
}
```

Nano 根据 `taskId` 执行预先定义的任务流程。

示例：

```text
任务 1：
1. 前进 300 mm。
2. 开始循迹。
3. 到达黑线末端。
4. 停车。

任务 2：
1. 循迹到第一个路口。
2. 右转 90°。
3. 定距前进 500 mm。
4. 停车。
```

第一版预设任务采用代码或配置文件定义，不在串口屏上编辑任务步骤。

## 4. 系统状态机

Nano 维护上层系统状态。

```text
DISCONNECTED
IDLE
ARMED
MANUAL
EXECUTING
COMPLETED
SAFE_STOP
FAULT
```

状态说明：

| 状态 | 含义 |
| --- | --- |
| DISCONNECTED | Nano 与 MSPM0 未建立有效通信 |
| IDLE | 已连接，车辆未使能 |
| ARMED | 已使能，可以接收运动命令 |
| MANUAL | 正在执行手动连续控制 |
| EXECUTING | 正在执行离散动作或预设任务 |
| COMPLETED | 最近任务正常完成，随后可回到 ARMED |
| SAFE_STOP | 急停或通信故障导致安全停车 |
| FAULT | MSPM0 报告硬件、传感器或控制故障 |

第一版规则：

1. 同一时间只允许一个活动离散动作或预设任务。
2. 手动控制开始前，应取消或停止当前离散任务。
3. 执行预设任务期间，普通运动按钮应被拒绝或先取消任务。
4. 急停在任何状态都必须有效。
5. `clear_fault` 只能清除允许软件恢复的故障。
6. 急停后不能自动恢复运动，必须重新 ARM。

## 5. 硬件链路

## 5.1 TJC—ESP32-S3 UART

串口参数：

```text
波特率：115200
数据位：8
停止位：1
校验位：无
流控：无
```

建议接线：

```text
ESP32-S3 GPIO4 TX -> TJC RX
ESP32-S3 GPIO6 RX <- TJC TX
ESP32-S3 GND      -> TJC GND
```

Arduino 初始化：

```cpp
Serial1.begin(115200, SERIAL_8N1, 5, 4);
```

要求：

- TX 和 RX 交叉连接。
- TJC 与 ESP32 必须共地。
- ESP32 RX 不得承受超出芯片允许范围的电平。
- 串口屏供电根据实际型号确定。
- TJC 不直接生成 Nano—MSPM0 二进制帧。

## 5.2 ESP32-S3 SoftAP

地面站 ESP32-S3 建立热点：

```text
SSID：CAR-GS-xxxx
AP IP：192.168.4.1
子网掩码：255.255.255.0
TCP 端口：8765
最大 Nano 连接数：1
```

要求：

- 使用 WPA2 密码。
- 密码通过配置写入，不提交到公开仓库。
- 第一版只允许 Nano 连接控制端口。
- 不要求互联网转发。
- 不要求 NAT。

## 5.3 Nano Wi-Fi

Nano 作为 Wi-Fi Station：

```text
连接 SSID：CAR-GS-xxxx
ESP 地址：192.168.4.1
Nano 地址：DHCP 或固定 192.168.4.2
TCP 地址：192.168.4.1:8765
```

要求：

- 设置为自动连接。
- 关闭可能导致频繁断线的激进省电。
- 控制链路与校园网、互联网无关。
- 调试 SSH 可使用另一张网卡、有线网络或 Tailscale。

## 5.4 Nano—MSPM0 UART

继续使用现有 Nano—MSPM0 协议。

建议参数：

```text
波特率：115200
数据位：8
停止位：1
校验位：无
流控：无
电平：3.3 V TTL
```

Nano 侧只能有一个串口工作线程持有该 UART。

网络线程、状态线程和任务线程不得同时直接读写串口。

注意 Nano—MSPM0 的安全心跳与 ESP—Nano 的 1 s 网络心跳不同。当前 V1.1
规定：Nano 发起 ARM 或运动后，必须每 100 ms 向 MSPM0 发送 HEARTBEAT；连续
500 ms 未收到合法 Nano 帧时 MSPM0 停车并以 `LINK_LOST` 结束 Nano 来源事务。
Nano 不得因为 ESP—Nano 连接正常就降低或跳过该串口心跳。

## 6. ESP32—Nano TCP 传输

## 6.1 网络角色

```text
ESP32-S3：TCP Server
Jetson Nano：TCP Client
```

选择该角色是为了：

- ESP 地址固定为 `192.168.4.1`。
- Nano 自动连接固定地址。
- ESP 重启后 Nano 自动重连。
- TJC 与 ESP 属于同一个地面站设备。

TCP 是全双工连接。

ESP 可以发送命令，Nano 可以主动发送状态。

TCP 连接建立后，Nano 只接受完成 `hello / hello_ack` 的会话中的普通命令。
ESP 在每次启动时生成随机、非零的 `groundStationSessionId`；一条命令的上层
幂等键是 `(groundStationSessionId, id)`，而不是单独的 `id`。Nano 必须为转给
MSPM0 的异步操作另行分配 V1.1 `sessionId` 和 `commandId`，不能把 ESP 的 `id`
直接当作 MSPM0 的事务编号。

## 6.2 消息封装

TCP 是字节流，不能认为一次 `send()` 就对应一次 `recv()`。

每条消息使用：

```text
4 字节小端 JSON 长度
+
UTF-8 JSON 内容
```

格式：

```text
+------------------+----------------------+
| JSON Length LE32 | UTF-8 JSON           |
+------------------+----------------------+
       4 Byte            1..4096 Byte
```

接收端必须：

1. 收满 4 字节。
2. 解析小端长度。
3. 检查长度范围 `1..4096`。
4. 收满完整 JSON。
5. 使用 UTF-8 解码。
6. 解析为 JSON 对象。
7. 处理后继续读取下一帧。

遇到以下错误关闭当前连接：

- 长度为 0。
- 长度超过 4096。
- UTF-8 解码失败。
- JSON 解析失败。
- JSON 根节点不是对象。
- 必需字段类型错误。

TCP 链路不额外使用 COBS 或 CRC16。

发送规则：

- 两端使用非阻塞 socket；命令帧最大 512 B，普通 `status` 最大 1024 B。
- 普通状态在进入队列前合并为最新一条；无法及时写出时丢弃旧状态。
- 手动刷新只保留最新一条，不能因 TCP 发送阻塞积累多个历史方向命令。
- `stop` 和 `estop` 必须绕过普通状态队列立即尝试写出，但不能宣称 TCP 能抢占
  已经交给内核发送的字节。
- 连接写阻塞、半关闭、解析错误或心跳超时均按断链处理；物理急停仍是唯一可
  独立依赖的紧急停车手段。

## 6.3 连接建立

ESP 启动：

```text
初始化 TJC UART
-> 启动 SoftAP
-> 监听 TCP 8765
-> 等待 Nano
```

Nano 启动：

```text
启动 Wi-Fi
-> 连接 CAR-GS-xxxx
-> TCP 连接 192.168.4.1:8765
-> 发送 hello
-> 接收 hello_ack
-> 建立 Nano—MSPM0 链路
-> 向 ESP 发送 snapshot
```

Nano hello：

```json
{
  "v": 1,
  "type": "hello",
  "role": "nano",
  "version": "2.1"
}
```

ESP 回复：

```json
{
  "v": 1,
  "type": "hello_ack",
  "role": "esp32",
  "version": "2.1",
  "groundStationSessionId": 284920173
}
```

`hello` / `hello_ack` 还用于建立本次地面站会话；普通命令均带回显的
`groundStationSessionId`。第一版不做互联网访问或复杂认证，但 WPA2 密码
仍不得提交到仓库。

## 6.4 心跳

ESP 每 1 秒发送：

```json
{
  "v": 1,
  "type": "heartbeat",
  "source": "esp32",
  "uptimeMs": 12345
}
```

Nano 每 1 秒发送：

```json
{
  "v": 1,
  "type": "heartbeat",
  "source": "nano",
  "uptimeMs": 67890,
  "tiOnline": true
}
```

在线判断：

```text
0～3 秒内收到有效消息：UP
3～5 秒未收到有效消息：DEGRADED
超过 5 秒：DOWN，关闭并重连
```

任意合法消息均可刷新连接活性时间。

## 6.5 重连

Nano 断线后使用退避：

```text
第 1 次：500 ms
第 2 次：1 s
第 3 次：2 s
后续：5 s
连接稳定 30 s 后重置
```

ESP 同一时间只接受一个 Nano 连接。

新连接到来时：

- 旧连接已经失效：关闭旧连接，接受新连接。
- 旧连接仍正常：拒绝新连接。

## 6.6 发送优先级

从高到低：

1. `estop`
2. `stop`
3. `cancel`
4. `accepted / rejected / done / failed`
5. 关键故障和状态变化
6. 心跳
7. 普通周期状态

普通状态只保留最新一条。

不得因为状态堆积阻塞急停。

## 7. 统一 JSON 基础格式

所有消息包含：

```json
{
  "v": 1,
  "type": "command",
  "groundStationSessionId": 284920173
}
```

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| v | int | 协议版本，第一版固定为 1 |
| type | string | 消息类型 |
| groundStationSessionId | uint32 | ESP 本次启动的随机非零会话号；所有 command 必填 |
| id | uint32 | 命令编号，仅命令和命令结果需要 |
| cmd | string | 命令名称 |
| args | object | 命令参数 |

ESP 在同一 `groundStationSessionId` 内为每个新的逻辑命令生成单调递增的 `id`。
重发同一逻辑命令时必须保留相同的 `id` 和参数；ESP 重启后可从 1 重新开始，
因为新的 `groundStationSessionId` 已将其隔离。

`id` 用于关联：

- command
- accepted
- rejected
- done
- failed

Nano 只用该键关联地面站请求与结果；它向 MSPM0 分配的 `commandId` 保持独立。

## 8. 命令定义

## 8.1 ARM

请求：

```json
{
  "v": 1,
  "type": "command",
  "groundStationSessionId": 284920173,
  "id": 1,
  "cmd": "arm",
  "args": {}
}
```

作用：

- 请求 MSPM0 进入可执行运动命令状态。
- 车辆故障或 SAFE_STOP 未恢复时应拒绝。

## 8.2 DISARM（上层准入锁）

```json
{
  "v": 1,
  "type": "command",
  "groundStationSessionId": 284920173,
  "id": 2,
  "cmd": "disarm",
  "args": {}
}
```

作用：

- Nano 先取消活动事务并等待停车终态，再关闭自己的运动命令准入。
- 之后 ESP 的运动命令被 Nano 拒绝，直到新的 `arm` 已完成。
- 当前 Nano—MSPM0 V1.1 没有独立 `DISARM` 帧；因此该命令**不能**宣称已让
  MSPM0 退出 READY，也不能代替 `estop` 或物理断电。若需要硬件级失能，先扩展
  Nano—MSPM0 协议并在两端实现。

## 8.3 手动控制

```json
{
  "v": 1,
  "type": "command",
  "groundStationSessionId": 284920173,
  "id": 10,
  "cmd": "manual_drive",
  "args": {
    "linearMmPerSec": 200,
    "angularMdegPerSec": 0,
    "manualSeq": 1
  }
}
```

参数：

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| linearMmPerSec | int | 前后线速度，正数前进，负数后退 |
| angularMdegPerSec | int | 角速度，正负方向由项目统一约定 |
| manualSeq | uint32 | 同一次按住期间严格递增的刷新序号 |

典型映射：

```text
前进：linear > 0，angular = 0
后退：linear < 0，angular = 0
左转：linear = 0，angular > 0
右转：linear = 0，angular < 0
左前：linear > 0，angular > 0
右前：linear > 0，angular < 0
```

`manual_drive` 仅在 Nano—MSPM0 的受限速度命令已实现、限幅并通过失联测试后
允许使用。按钮按下时 ESP 分配一个逻辑 `id`，在该次按住期间保持此 `id` 不变，
每 100 ms 递增 `manualSeq` 并重发最新目标；不要为每一帧分配新 `id`。

Nano 超过 300 ms 未收到新的 `manual_drive`，必须停车。

Nano 只在第一次成功进入 MANUAL 时返回一次 `accepted`，不对每个刷新返回
`accepted`。停止、超时、取消或故障后，Nano 只为该逻辑 `id` 发送一次终态。
如此不会因每秒 10 次确认而堵塞控制链路。

Nano 对合法手动命令可以返回轻量确认：

```json
{
  "v": 1,
  "type": "accepted",
  "id": 10,
  "state": "MANUAL"
}
```

## 8.4 STOP

```json
{
  "v": 1,
  "type": "command",
  "groundStationSessionId": 284920173,
  "id": 20,
  "cmd": "stop",
  "args": {}
}
```

作用：

- 对当前 Nano—MSPM0 V1.1 活动事务，Nano 必须转换为携带目标 `commandId` 的
  `CANCEL`，并等待受控停车：原事务以 `USER_CANCELLED` 失败，CANCEL 自身
  `done`。没有活动事务时 Nano 立即返回 `done`。
- 退出手动模式。
- 停止当前普通运动。
- 不等同于锁存急停。

## 8.5 ESTOP

```json
{
  "v": 1,
  "type": "command",
  "groundStationSessionId": 284920173,
  "id": 21,
  "cmd": "estop",
  "args": {}
}
```

作用：

- 最高优先级。
- 立即请求 MSPM0 进入 SAFE_STOP。
- 清空 Nano 普通待执行任务。
- 锁存 SAFE_STOP（当前 V1.1 会报告 `EMERGENCY_STOPPED` 安全锁存）。
- 不能通过重新连接自动解除。

恢复流程：

```text
ESTOP
-> SAFE_STOP
-> clear_fault
-> IDLE
-> arm
-> ARMED
```

无线急停不能替代车体物理急停。

## 8.6 CLEAR_FAULT

```json
{
  "v": 1,
  "type": "command",
  "groundStationSessionId": 284920173,
  "id": 22,
  "cmd": "clear_fault",
  "args": {}
}
```

作用：

- 请求 MSPM0 清除允许恢复的故障。
- 硬件故障仍存在时应失败。

## 9.5 命令生命周期

```text

-> accepted
-> done
```

或：

```text

-> accepted
-> failed
```

或：

```text
command
-> rejected
```

- 已发送。
- 已受理。
- 执行中。
- 已完成。
- 执行失败。
- 被拒绝。

- 任务步骤变化。

## 11.2 任务执行器

Nano 实现 `TaskRunner`。

职责：

1. 根据 taskId 加载任务。
2. 检查当前系统是否允许执行。
3. 按顺序提交步骤。
4. 等待每一步 `done`。
5. 某一步 `failed` 后终止整个任务。
6. 接收 `cancel` 和 `estop`。
7. 发布任务进度。

任务进度消息：

```json
{
  "v": 1,
  "type": "task_progress",
  "taskId": 2,
  "stepIndex": 1,
  "stepCount": 4,
  "stepName": "drive_distance",
  "state": "EXECUTING"
}
```

任务失败：

```json
{
  "v": 1,
  "type": "failed",
  "id": 40,
  "taskId": 2,
  "reason": "TASK_STEP_FAILED",
  "failedStepIndex": 2,
  "stepReason": "TURN_TIMEOUT"
}
```

## 11.3 任务中断

优先级：

```text
estop > stop > cancel > 当前任务步骤
```

`estop`：

- 立即终止。
- 清空任务。
- 进入 SAFE_STOP。

`cancel`：

- 停止当前步骤。
- 标记任务取消。
- 回到 ARMED 或 IDLE。

`stop`：

- 按 8.4 转换为对活动 MSPM0 事务的 `CANCEL`。
- 第一版中 `stop` 必须同时终止当前 Nano 任务，避免“底盘已停而 TaskRunner
  又继续下一步”的状态不一致。

- 手动命令交给手动控制逻辑。
- 离散动作交给 `CarSerialWorker`。
- 预设任务交给 `TaskRunner`。
- stop、cancel、estop 使用高优先级通道。
- 同一时间只允许一个活动离散任务。

## 14.4 `CarSerialWorker`

整个进程中唯一允许访问 Nano—MSPM0 UART 的模块。

职责：

- HELLO。
- HEARTBEAT。
- GET_STATUS。
- 发送 ARM、CANCEL、EMERGENCY_STOP 等 V1.1 串口命令；上层 `stop` 必须在
  CommandDispatcher 中映射为 CANCEL，不能伪造一个不存在的串口 STOP 帧。
- 发送运动命令。
- 解析 ACK、DONE、FAILED、STATUS。
- 将事件发送到线程安全事件队列。
- 最多每 20 ms 检查一次高优先级命令。

禁止：

- TCP 线程直接调用 `CarSerialLink`。
- TaskRunner 直接读串口。
- 状态线程直接读串口。
- 多线程同时调用 `CarSerialLink`。

## 14.5 `TaskRunner`

职责：

- 加载任务。
- 顺序执行步骤。
- 等待步骤终态。
- 推送进度。
- 处理取消。
- 处理步骤失败。
- estop 时立即终止。

## 14.6 `StateStore`

保存：

- ESP—Nano 状态。
- Nano—TI 状态。
- MSPM0 状态。
- 当前命令。
- 当前任务。
- 最近终态。
- 故障码。
- 轮速。
- 循迹误差。
- 已由 MSPM0 或专用任务可靠提供的事件计数；不得把通用角点数推导为圈数。

所有状态推送从 `StateStore` 生成，避免多个模块自行拼 JSON。

## 15. 手动控制安全规则

手动控制必须满足以下全部规则。

1. ESP 仅在按钮处于按下状态时刷新。
2. 刷新周期 100 ms。
3. Nano 手动命令超时 300 ms 自动停车。
4. TCP 断开后立即停车。
5. ESP 心跳超时后立即停车。
6. Nano 进程退出时，MSPM0 依靠 Nano 心跳超时停车。
7. 新的方向按下覆盖旧方向。
8. 多个方向键冲突时使用明确组合规则。
9. release 事件立即发送 stop。
10. 急停永远高于手动命令。
11. 未 ARM 时拒绝手动运动。
12. FAULT 和 SAFE_STOP 状态拒绝手动运动。
13. Nano 只接受当前 `groundStationSessionId` 中 `manualSeq` 大于已处理值的刷新；
    会话重连或切换时先停止手动模式，再等待新的 `hello_ack`。
14. ESP 的 TCP 发送队列中不得保留历史 `manual_drive`；按钮 release 后立即使
    本地手动状态失效并发送 `stop`，不能等待下一次 100 ms 刷新。

建议 ESP 内部保存：

```cpp
struct ManualDriveState {
    bool active;
    int32_t linear_mm_s;
    int32_t angular_mdeg_s;
    uint32_t last_send_ms;
};
```

建议 Nano 保存：

```python
@dataclass
class ManualControlState:
    active: bool = False
    linear_mm_s: int = 0
    angular_mdeg_s: int = 0
    last_update_monotonic: float = 0.0
```

## 17. 断链行为

| 故障 | 行为 |
| --- | --- |
| TJC—ESP 串口异常 | ESP 显示界面故障，不生成新命令 |
| ESP—Nano TCP 断开 | Nano 立即停止手动控制；对当前地面站发起的离散动作或 `run_task` 发送 CANCEL，任务以 `LINK_LOST` 失败 |
| ESP 重启 | 手动控制立即失效；Nano 超时停车 |
| Nano 进程崩溃 | MSPM0 因 Nano 心跳超时停车 |
| Nano—MSPM0 串口断开 | Nano 报 TI_OFFLINE，拒绝新运动命令 |
| MSPM0 重启 | Nano 重新 HELLO；当前任务标记失败 |
| TJC release 丢失 | Nano 因 300 ms 手动刷新超时停车 |
| 普通状态发送阻塞 | 丢弃旧状态，不影响 stop 和 estop |

第一版的断链策略是确定的，而不是“可继续或可停止”的可选项：只要动作由当前
地面站会话启动，ESP—Nano 链路断开就停止该动作。这样操作员失去状态画面时
车辆不会继续运行。以后若比赛规则明确需要失去地面站后继续完成任务，应增加
单独的“自主任务”授权、明确的赛前启动方式和实车失联测试；不得悄悄复用
`run_task` 的默认行为。

## 19. 开发实施顺序

Codex 必须按阶段开发，不得一次性堆完所有功能。

## 阶段 0：确认 Nano—MSPM0 基线

目标：

- 不修改现有协议语义。
- 确认 HELLO、HEARTBEAT、GET_STATUS。
- 确认 ARM、CANCEL、EMERGENCY_STOP。
- 确认现有运动命令接口。
- 记录 HELLO capability flags 与本说明书 1.1 的差异，作为 UI 启用条件。

验收：

- Nano 能稳定读取 MSPM0 状态。
- Nano 断开后 MSPM0 能按现有规则停车。
- 不接电机或架空车轮测试。
- 明确当前 V1.1 不支持 `manual_drive`、倒车、独立 `disarm` 和通用圈数完成。

## 阶段 1：ESP SoftAP + Nano TCP

ESP：

- 建立热点。
- TCP Server 8765。
- 长度前缀 JSON。
- hello。
- heartbeat。

Nano：

- 自动连接热点。
- TCP Client。
- 长度前缀 JSON。
- 自动重连。
- hello。
- heartbeat。

验收：

- 连续运行 30 分钟。
- ESP 和 Nano 任一重启后恢复。
- 半包、粘包可正确解析。
- 无车辆运动命令。

## 阶段 2：状态贯通

Nano：

- 读取 MSPM0 状态。
- 生成 snapshot 和 status。

ESP：

- 接收 status。
- 显示到 TJC。

验收：

- TJC 显示 AP、Nano、TI 状态。
- 显示 armed、fault、轮速、循迹误差。
- 普通状态不超过 10 Hz。

## 阶段 3：基础安全命令

实现：

- arm。
- 上层 disarm（Nano 准入锁，非 MSPM0 DISARM 帧）。
- stop。
- estop。
- clear_fault。
- get_status。

验收：

- 车轮架空。
- estop 高优先级。
- SAFE_STOP 不能自动解除。
- 断链停车行为正确。

## 阶段 4：手动连续控制

实现：

- 方向按钮 press/release。
- ESP 100 ms 刷新。
- Nano 300 ms 超时停车。
- 前进、后退、左转、右转。
- 后续再增加斜向组合。

前置条件：先完成 Nano—MSPM0 V1.2 受限 `MANUAL_DRIVE` 的帧定义、参数限幅、
单串口线程实现、MSPM0 看门狗和车轮架空/低速实车测试。该协议变更必须同步
更新两端说明、代码与测试；在此前本阶段不得开始实现 UI 手动控制。

验收：

- 按住前进持续运动。
- 松开立即停车。
- 拔掉 Wi-Fi 后停车。
- ESP 重启后停车。
- release 丢失后 300 ms 左右停车。

## 阶段 5：离散动作

依次实现：

1. 仅前进的 drive_distance。
2. turn_relative。
3. follow_line。
4. cancel。

倒车和专用圈数任务不是本阶段的隐含内容：它们分别需要有符号距离扩展和经过
赛道验证的圈检测，再单独增加验收项。

每次只增加一种动作。

验收：

- accepted 只代表 MSPM0 已接受。
- 完成后返回 done。
- 超时或故障返回 failed。
- 同一时间只执行一个离散动作。

## 阶段 6：预设任务

实现：

- tasks.json。
- TaskLoader。
- TaskRunner。
- task_progress。
- run_task。
- cancel。

验收：

- 能执行至少两个预设任务。
- 步骤失败后整个任务停止。
- 任务中可以 cancel。
- estop 能立即中断任务。

## 22. Codex 开发约束

Codex 必须遵循以下要求。

1. 先阅读现有 ESP、Nano 和 MSPM0 代码，再修改。
2. 未经双方同步修改不得假定 Nano—MSPM0 V1.1 支持新能力；扩展协议时必须同时
   更新协议说明、Nano 客户端、MSPM0 固件和测试。
3. 不在 ESP 侧复制 MSPM0 二进制协议。
4. 不让多个 Nano 线程同时访问串口。
5. 不在网络回调中直接执行耗时任务。
6. 所有命令参数集中校验。
7. 所有状态从统一 StateStore 生成。
8. stop 和 estop 使用高优先级队列。
9. 手动控制必须有超时停车。
10. 每完成一个阶段先补测试，再进入下一阶段。
11. 不做与当前阶段无关的大规模重构。
12. 保留用户现有修改。
13. 新增配置必须提供默认值和示例文件。
14. 日志应便于定位连接、命令和任务问题。
15. 所有角度、速度、距离单位写入字段名。
16. 不允许使用模糊字段名，例如 `speed`、`angle`、`value`。
17. 对外 JSON 使用 camelCase。
18. Python 内部可使用 snake_case。
19. C++ 内部遵循现有项目风格。
20. 每个阶段提交前输出：
    - 修改文件列表。
    - 核心设计说明。
    - 测试命令。
    - 测试结果。
    - 尚未完成内容。
    - 下一阶段建议。

## 25. 最终结论

本系统的控制关系必须始终保持：

```text
地面站决定“做什么”
Nano 决定“按什么任务流程做”
MSPM0 决定“电机具体怎么做”
```

地面站提供：

```text
手动前进、后退、转向
定距、定角度、循迹
预设任务
停止、取消、急停
状态显示
```

ESP32 只负责界面和网络。

Nano 只负责业务命令、任务仲裁和状态汇总。

MSPM0 负责所有实时运动控制和最终安全停车。
